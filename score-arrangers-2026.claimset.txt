DEFINITIONS
D1 [entity] arranging system: A software product, online service or research system that, from existing musical material (a melody, chords, a score or a performance), automatically or semi-automatically produces parts for instruments: by orchestrating, harmonising, voicing, exploding or reducing. The unit of analysis: one system, counted once across versions and editions.
D2 [concept] notated output: The system delivers its arrangement as notation a musician reads: a score or parts in standard staff notation, exported as MusicXML, PDF or a notation application's file, or written into a notation editor. [qualitative: code {"include": "The system's own description or documentation shows the arrangement as staff notation, or exports MusicXML, PDF score/parts, or a notation-app file.", "exclude": "Output only as audio, MIDI without notation, tablature or chord charts alone, or piano-roll."}]
D3 [concept] user-chosen instrumentation: The user selects the instruments or ensemble the arrangement is written for. [qualitative: code {"include": "The user picks target instruments, an ensemble, or a template of instruments, and the parts are written for that choice.", "exclude": "A fixed instrumentation (e.g. piano only, or a style's fixed band) the user cannot change instrument by instrument."}]
D4 [concept] score input: The system accepts notated music as its input. [qualitative: code {"include": "Accepts MusicXML, or works on a score inside a notation application (which reads MusicXML).", "exclude": "Accepts only audio, MIDI, chord symbols, text prompts or live playing."}]
D5 [concept] ML method: The arrangement is produced by a model trained on data (machine learning, neural network, LLM). [qualitative: code {"include": "The developer states that a trained model (machine learning, neural network, deep learning, LLM, 'AI model') generates the arrangement.", "exclude": "'AI' used as a label without saying that a trained model produces the arrangement; such systems are coded unclear method."}]
D6 [concept] rules method: The arrangement is produced by hand-written rules, styles, templates or algorithms without a trained model. [qualitative: code {"include": "The developer describes style files, templates, rules, voice-leading algorithms or search procedures, or an independent review does.", "exclude": "Any trained model generating the arrangement."}]
D7 [concept] unclear method: The sources do not say whether a trained model or rules produce the arrangement. [qualitative: code {"include": "Marketed as 'AI' or 'intelligent' with no statement of how the arrangement is produced.", "exclude": "Either ML method or rules method applies."}]
D8 [concept] interactive or real-time: The arrangement is regenerated in response to the user's choices or playing without an offline export-import cycle. [qualitative: code {"include": "Arrangement updates live as the user plays, changes instruments or settings, within the same session.", "exclude": "A one-off batch generation the user must re-run from scratch."}]
D9 [concept] commercially available: Sold or licensed to the public (paid, subscription or freemium) at the date of retrieval. [qualitative: code {"include": "A price, subscription or purchase page exists at retrieval.", "exclude": "Free open-source, free-only, discontinued, or research-only systems."}]
D10 [concept] free or open-source: Available to the public at no cost at retrieval. [qualitative: code {"include": "Free download or free web use, or published code.", "exclude": "Paid-only or research descriptions without public access."}]
D11 [concept] research prototype: Described in a research publication (paper, preprint, thesis) rather than offered as a product. [qualitative: code {"include": "The source is a paper, preprint or thesis describing the system.", "exclude": "A product whose maker also published a paper is coded by its availability as a product."}]
D12 [concept] full-match arranger: A commercially available arranging system, not made by Syntonic Labs, that takes score input and uses an ML method to produce notated output for a user-chosen instrumentation. [qualitative: code {"include": "The same system is coded commercially available, score input, ML method, notated output and user-chosen instrumentation.", "exclude": "Any of the five missing, or the system is a Syntonic Labs product (Tempered)."}]
D13 [design] market scan: A fixed set of web searches run on one or two days, each result screened against the inclusion criteria, with one level of snowballing from included roundups, then each included system coded by a fixed codebook (summative content analysis, deductive).
D14 [concept] one-time purchase: Sold for a single payment (a perpetual licence), possibly with paid upgrades. [qualitative: code {"include": "A one-off price or perpetual licence is listed at retrieval.", "exclude": "Subscription-only or free."}]
D15 [concept] subscription: Paid by recurring fee (monthly or yearly), or by credits bought repeatedly. [qualitative: code {"include": "A monthly or yearly price, or credit packs, listed at retrieval.", "exclude": "One-off purchase only, or free."}]
D16 [concept] free tier: A free version or free use exists alongside paid options (freemium), or the system is wholly free. [qualitative: code {"include": "Free plan, free version, free trial longer than a demo, or wholly free use.", "exclude": "Time-limited trial of a paid product only, or no public access."}]
D17 [concept] price not stated: No price could be found in the dossier. [qualitative: code {"include": "The dossier shows no price or pricing model.", "exclude": "Any price or pricing model stated."}]
D18 [concept] desktop application: Runs as a standalone application on a computer. [qualitative: code {"include": "Downloadable standalone program for Windows, macOS or Linux.", "exclude": "Runs only inside another host (plugin) or in a browser."}]
D19 [concept] web service: Used in a web browser or through an online API. [qualitative: code {"include": "Browser-based app or online API.", "exclude": "Desktop-only or plugin-only."}]
D20 [concept] DAW plugin: Runs inside a digital audio workstation (VST, AU, AAX, MIDI effect). [qualitative: code {"include": "Offered in a DAW plugin format.", "exclude": "Notation-app plugins; standalone apps only."}]
D21 [concept] notation-app plugin or feature: Runs inside a notation application (Sibelius, Dorico, MuseScore, Finale) as a plugin or built-in feature. [qualitative: code {"include": "A notation application's own feature, or a plugin for one.", "exclude": "Exports to a notation app without running inside it."}]
D22 [concept] mobile app: Runs as an app on a phone or tablet. [qualitative: code {"include": "iOS, iPadOS or Android app.", "exclude": "Mobile web only (coded web service)."}]
D23 [concept] code or model only: Available only as source code, a library or model weights, with no packaged application. [qualitative: code {"include": "Published code, library or weights only.", "exclude": "Any packaged application, plugin or web service."}]

LIMITATIONS
L1 [deviation; affects C2; could_bias_magnitude; mitigation partial] Lab plan PL2 was made void (DC3): a defect made its runs (RN3, RN4) meaningless. DV1: tally.py kept only codings whose pass equals the integer 1, but the record stores pass as the string '1', so it counted no coding: every count in RN3 is 0. DV2: agreement.py compared pass with the integers 1 and 2, but the record stores pass as strings, so it found no dossier coded by both coders and computed no agreement. This claim is from plan PL3, which repeats it with the same analysis, reworded (both texts are in the exploration summary), and decision rule on the same data. PL3 was planned after the void runs and before its own, so what the void runs showed could have shaped it. The void runs returned only zeros for every count and no agreement values; no coding or count of any system was visible in them, so they showed nothing that could have shaped PL3 beyond the bug itself.
L2 [analytic_flexibility; affects C2; could_bias_magnitude; mitigation none] Plan PL3 was written after the dossiers had been coded (it re-runs PL2's analysis after a bug fix), so the codings of its counts precede its plan; the codebook, the codings and the analysis are those fixed under PL2, unchanged.
L3 [sampling; affects C1, C2; could_bias_magnitude; mitigation none] The scan covers only systems that 20 fixed web queries (and one level of snowballing) returned on 19 November 2026; products seen in an earlier ad-hoc search but not returned (Orb Composer, LANDR Composer, InstaComposer, Muse, RapidComposer, Texturium) are not in the counts, and a negative or positive count holds for this frame only.
L4 [measurement; affects C1, C2; could_bias_magnitude; mitigation none] Dossiers were built from WebFetch renderings of each page by a language model and from search snippets, not from byte copies of the pages; a feature a page states could be missed or misrendered, and several dossiers (Dorico, Chord Dock, Finale, research papers) rest on snippets or summaries.
